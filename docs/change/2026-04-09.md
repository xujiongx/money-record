# 2026-04-09 变更摘要

## 小布对话历史：客户端缓存与预取

**背景**：每次打开对话浮层都会清空列表并调用 `fetchChatMessagesAction`，体感偏慢。

**改动**：逻辑集中在 **`components/features/chat/useChatHistoryLoader.ts`**（`useChatHistoryLoader`），`FloatingChatBot.tsx` 只负责编排对话与 UI。

**行为**（`useChatHistoryLoader`）：

1. **内存缓存**：`historyCacheRef` 保存最近一次成功拉取的消息列表（最多 300 条，与 `app/actions/chat-history` 的 `CHAT_FETCH_LIMIT` 对齐）。
2. **Stale-while-revalidate**：若已有缓存，打开浮层时**立即**展示缓存内容（不再先清空再转圈），同时在后台仍发起同一次拉取以与数据库对齐。
3. **并发去重**：`historyInflightRef` 合并同时进行的多处请求（例如预取与首次打开），避免重复打 Supabase。
4. **空闲预取**：`mounted` 后通过 `requestIdleCallback`（无则 `setTimeout`）在空闲时预取历史，用户首次点小布前数据往往已就绪。
5. **写后更新缓存**：`persistChatExchangeAction` 成功后调用 `pushExchangeToCache`，减少关闭再打开时的陈旧感。

**说明**：缓存随页面刷新清空；换家庭需整页导航后自然失效。首页等业务页的加载速度仍主要取决于 RSC 上的 `fetchMembers` / `fetchTransactions` 等，与本次对话优化无关。

## Tab 切换：服务端 household 缓存 + 客户端路由预取

**背景**：底部 Tab 切换时每个页面都是动态 RSC，此前**每次导航**都会再打 Supabase `households` 表把 Cookie 中的编码解析为 `household_id`（与成员/流水的 `unstable_cache` 不同步）。

**改动**：

1. **`app/actions/ledger.ts`**：`requireHouseholdId` 内对「规范化后的家庭编码 → `household_id`」使用 **`unstable_cache`**（`revalidate: 120`，标签 **`ledger`**），与 `fetchMembers` / `fetchTransactions` 一并随 `revalidateTag("ledger", "max")` 失效。
2. **`components/common/usePrefetchAppTabs.ts`** + **`MobileShell`**：在非 `/login` 路由下，用 **`requestIdleCallback`**（或短延迟 `setTimeout`）对 `/`、`/record`、`/stats`、`/members` 调用 **`router.prefetch`**，提前拉取各 Tab 的 RSC payload（与 `Link` 自带预取互补，覆盖进入应用后尚未 hover 的条目）。

3. **`next.config.ts`**：**`experimental.staleTimes.dynamic`** 设为 **120**（秒）。Next 默认对动态路由的客户端缓存为 **0**，切 Tab 会反复请求 RSC，体感像「整页重载」；拉长后可在短时间内复用已预取的 Flight（仍非浏览器层面的多页 DOM 常驻，见下）。
